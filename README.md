# 育兒同行 Alongside

新北市與臺北市幼兒園與托嬰中心的資訊整理站。純靜態，部署在 Firebase Hosting 免費方案，現金支出 0 元。

規劃背景與決策理由見 [托育網站規劃文件.md](托育網站規劃文件.md)，設計規格見 [ui-mockup.html](ui-mockup.html)。

## 它做什麼

把散在好幾個網站的資訊集中成一頁：機構基本資料、幼兒園月費、裁罰紀錄，
地圖與家長評價連到 Google 地圖，評鑑與補助導向主管機關的官方查詢頁。

本站不評分、不排名、不轉載評論。

## 資料來源與其限制

**一、各縣市政府的開放資料**（每月自動抓取）

| 縣市 | 幼兒園 | 托嬰中心 | 幼兒園骨幹 |
| --- | --- | --- | --- |
| 新北市 | 1,111 | 382 | 市府開放資料 |
| 臺北市 | 743 | 252 | **民間封存** |

**兩市的資料韌性不同，這點不能含糊。** 新北市有市府層級的幼兒園名冊，
封存只是加值層——上游消失時新北的幼兒園還在，只失去收費與裁罰。
臺北市沒有對應的市府開放資料，幼兒園名冊本身就取自封存，上游消失就整批不見。
`institutions.json` 的 `cities[].preschoolBackbone` 記錄這個差異，授權頁與頁尾都會照實說明。

托嬰中心則是各縣市自己發布，平台、格式、欄位全都不同，每加一個縣市就要寫一段剖析
（`fromNtpcNursery` / `fromTaipeiNursery`）。臺北市的 CSV 沒有行政區欄位，要從地址剖析；
私立那份也沒有收托人數。**這就是為什麼擴張的成本主要在托嬰，不在幼兒園。**

**二、台灣幼兒園地圖封存資料**（[kiang/ap.ece.moe.edu.tw](https://github.com/kiang/ap.ece.moe.edu.tw)，MIT 授權）

g0v 江明宗長期以自動化腳本備份全國教保資訊網，涵蓋全國 22 縣市，提供政府開放資料沒有的欄位：
分齡收費、裁罰明細、立案字號、核定人數、面積、座標、園所官網。
雙北 1,854 間幼兒園中 1,680 間有分齡收費、744 間有裁罰共 2,165 筆。

封存資料含已停辦機構與同名重複，兩者都會造成主鍵碰撞，處理方式見 `fetchInstitutions()`：
已停辦（`is_active=0`）不收錄；同名時一律以營運中的那筆為準——實測臺北市有搬遷案例
（舊址停辦、新址營運，兩筆同名），若讓後寫入的覆蓋，會把停辦分部的座標與收費掛到營運中的機構上。

這個來源有四個必須誠實面對的限制，程式與頁面上都做了對應處理：

| 限制 | 處理方式 |
| --- | --- |
| 不是政府開放資料，是民間對官網的備份 | 每個使用它的區塊都標示出處、作者、授權與備份日期 |
| 官方公告有時效會下架，備份可能留有官方已查不到的舊紀錄 | 機構頁的裁罰區塊置頂四點說明，並附官方即時查詢連結 |
| 只涵蓋幼兒園，382 間托嬰中心無對應資料 | 托嬰中心頁面不顯示這些欄位；概況頁明講統計不含托嬰 |
| 上游若停止維護，資料會無聲變舊 | `ARCHIVE_MAX_AGE_DAYS`（120 天）過期就整批不採用，頁面自動退回只有開放資料的版本 |

### 收費欄位的語意是驗證出來的，不是猜的

封存 GeoJSON 有一個 `monthly` 欄位，但它對 1,057 間中的 782 間（74%）對不上任何年齡的
實際收費，也不是各齡平均，來源無法解釋，已棄用。

改用 `summary1/新北市/{2,3,4,5}.csv` 的分齡資料。欄位語意用同一來源的收費明細表
（`slip114`，園所依法申報的原始文件）反推並交叉驗證：

| 等式 | 樣本驗證 |
| --- | --- |
| `monthly1 = total1 ÷ months` | 40/40 |
| 全學期總收費 = 學費＋雜費＋材料費＋活動費＋午餐費＋點心費 | 20/20 |
| `total1 = 上學期總收費 × 2` | 19/20 |
| `total2 = 課後延托費 × 2` | 17/20 |

結論：**`monthly1` 是每月必繳費用，未扣任何政府補助，不含交通費與課後延托費。**
`monthly2` 是課後延托費的月攤，屬選繳——一開始誤以為是補助，驗證後推翻。

因此頁面一律分齡呈現並標明年齡（2 歲與 5 歲可差三千以上），且明講「未扣補助」。
`收費月數` 同時用來回答家長最常問的「有沒有寒暑假」：12 個月為全年收費，
9 個月為學期制、寒暑假需另外安排——這是代理指標而非直接答案，頁面上有說明。

非營利與職場互助的收費全國都是同一個數字，那是政策訂的收費上限而非實際分布，
`feeByOwnership()` 會用 `flat` 標記。家數少於 10 間的類型不畫進圖表，只留在表格。

### 補助試算

本站顯示的是園所收費，不是家長實付。一間準公共園申報 12,274，家長第 1 胎其實只付
3,000，差額由政府直接撥給園所——沒有這層換算，家長並排看到「準公共 12,274」與
「私立 11,641」會以為差不多，實際差了四倍。這是主動誤導，不只是資訊不足。

`src/lib/subsidy.js` 集中所有政策數字（111 年 8 月起適用，取自教育部全國教保資訊網）：

| 類型 | 第 1 胎 | 第 2 胎 | 第 3 胎以上 | 低收／中低收 |
| --- | --- | --- | --- | --- |
| 公立 | ≤1,000 | 免費 | 免費 | 免費 |
| 非營利、職場互助 | ≤2,000 | ≤1,000 | 免費 | 免費 |
| 準公共 | ≤3,000 | ≤2,000 | ≤1,000 | 免費 |
| 私立等（育兒津貼） | 5,000 | 6,000 | 7,000 | — |

兩種補助的機制完全不同，UI 分開講：平價教保是**入學自動減免**，家長只繳上限內金額；
育兒津貼是**匯進家長帳戶**，要自己申請，學費照付。

準公共的上限明確涵蓋「學費、雜費、材料費、活動費、午餐費及點心費」，
正好就是本站 `monthly` 的六個項目，兩者可直接相減。

`verify.js` 把這四組數字釘住，改動時必須有意識地一起改。

### 加一個縣市要改哪裡

`scripts/fetch-data.js` 的 `CITIES` 陣列是唯一的設定入口，加一筆就多一個縣市。
但實際還要處理三件事，這就是每個縣市 2–3 天的來源：

1. **托嬰中心的剖析器**——各縣市欄位不同，要寫一個 `fromXxxNursery`。
2. **八個官方連結**——`src/lib/site.js` 的 `CITY_LINKS`。托嬰的四個各縣市完全不同；
   幼兒園只有「收退費」是地方的，裁罰與評鑑走全國教保資訊網、育兒津貼走教育部。
   連結一律用 `kind` 查找而非標籤文字：新北叫「裁罰公告」、臺北叫「違反兒少法公告」，
   用文字比對會在加新縣市時默默失效。
3. **行政區重名**——目前雙北 41 區無重名，網址可直接用區名。加入第三個縣市前
   要先確認（例如三民區、中正區在多個縣市都有），`verify.js` 有一條檢查會擋下。

**機構 ID 不含縣市**（`kind-名稱-行政區`）。新北市那 1,493 個網址已提交 Search Console，
擴充時不能改動，`verify.js` 有一條檢查釘住這件事。

### 拿不到的資料

- **上下課的實際時間**：收費明細表只區分半日班與全日班，沒有時刻。
- **托嬰中心的座標**：政府開放資料只給文字地址，地址定位服務需申請金鑰，決定不申請。
  因此距離排序只涵蓋幼兒園，頁面上明講。
- **名額、抽籤時程、師生比、教育理念**：無任何開放資料。

### 資料處理階段就過濾掉的東西

這些不是顯示層的隱藏，是在 `fetch-data.js` 就不寫進 `institutions.json`，
所以版控裡也不會有：

- **個人姓名。** 原始裁罰公告含「負責人：某某」「行為人：某某」，全市共 477 位可識別自然人。
  `toRole()` 只保留角色。家長選的是機構不是個人，而公開自然人的裁罰紀錄——尤其官方已下架之後——
  涉及個資與名譽，風險高於它帶來的價值。
- **不可信的園所連結。** `safeWebsite()` 擋掉學校內網 IP、缺 TLD 的殘缺網址、帶帳號資訊的網址
  （來源實際出現過打錯成 email 的 `http:/someone@yahoo.com.tw`，會被解析成 userinfo）、
  短網址與已停止服務的部落格平台，並輸出正規化後的 `url.href` 而非原始字串。
  553 筆過濾後剩 329 筆。

### 授權與聲明

`/授權/` 頁載明兩個來源的授權條款（政府資料開放授權條款第 1 版、MIT 完整聲明）、
本站對原始資料所做的加工、Google 商標聲明、字型未散布聲明，以及更正下架管道。
`DataNotice` 元件把「資料為程式自動整理、可能有誤、請以原始資料為準」的聲明
連同可點的原始資料集連結放在每一種頁型上，頁尾另有一份。

## 指令

```bash
npm install           # 安裝相依套件
npm run fetch         # 只抓資料，更新 institutions.json 與搜尋索引
npm run dev           # 本機開發伺服器 http://localhost:4321
npm run build         # 抓資料 + 建置 + 驗證
npm run build:offline # 用現有資料建置 + 驗證，不連網
npm run verify        # 只驗證 dist/
npm run cost          # 推估免費額度還能撐多少人
npm run preview       # 預覽 dist/ 的建置結果
```

`npm run verify` 的每一條檢查都對應一個真的發生過的問題（地址被誤切、罰鍰金額解析錯誤、
`[hidden]` 被樣式蓋掉導致篩選失效、個資外洩、主管機關連結給錯……），
不是理論風險。建置與 CI 都會跑，失敗就中止部署。

## 架構

```
scripts/fetch-data.js   下載開放資料 + 封存資料 → 正規化 → src/data/institutions.json
src/lib/site.js         全站設定：網址、標籤配色、官方連結對照表
src/lib/stats.js        建置期計算所有統計，瀏覽器端不做任何運算
src/lib/subsidy.js      補助政策數字與試算，集中一處方便隨政策更新
src/scripts/shortlist.js 收藏（localStorage，無後端無帳號）
scripts/verify.js       對建置產物做 46 項回歸檢查
src/pages/index.astro   首頁（年齡分流 + 29 個行政區入口 + 全市概覽圖表）
src/pages/附近.astro     用瀏覽器定位算直線距離，跨行政區
src/pages/搜尋.astro     機構名稱搜尋（前端比對 search-index.json，不含座標）
src/pages/收藏.astro     並排比較收藏的機構
src/pages/裁罰.astro     裁罰紀錄一覽，可依違規類型與行政區篩選
src/pages/概況.astro     新北市托育概況，完整圖表與資料來源說明
src/pages/授權.astro     資料來源與授權聲明
src/pages/d/[district]  行政區列表頁，共 41 頁；可疊加篩選、依費用排序
src/pages/i/[id]        機構頁，共 2,488 頁 ← SEO 主戰場
dist/                   建置產物，直接部署到 Firebase Hosting
```

建置產出 2,537 頁、約 59 MB。`npm run fetch` 約 20 秒（含 422 個裁罰明細檔與 4 份分齡收費）。

### 列表卡片的主要動作是「進內頁」

早期版本把「在 Google 地圖看評價」做成卡片上唯一像按鈕的元素，實測結果是使用者
全部點它、被帶離網站，從沒發現有整理過的內頁。現在整張卡是進內頁的連結
（標題連結以 `::after` 覆蓋整張卡），Google 地圖降為右下角的次要小連結。

### 篩選可疊加，不是單選

家長真正的需求是「收 2 歲 **而且** 公立」。早期版本一次只能選一個條件，
按了第二個就把第一個取消掉，等於不能用。現在每一類（機構別／屬性／年齡／裁罰）
彼此以 AND 相接，同一類內可複選、以 OR 相接。

### 收藏與比較

找托育是跨好幾週的事，家長會分很多次來看。收藏存在 `localStorage`：
不需要後端、不需要帳號、資料留在使用者裝置上，不影響純靜態與零成本，
也不用處理任何個資。代價是換裝置就沒了，這個取捨對本站划算。

`/收藏/` 用「機構當欄、欄位當列」的橫向表格——比較的重點是同一列互相對照，
縱向堆疊會讓人看不出差異。

### 首頁依年齡分流

站上的價值幾乎全在幼兒園（平均 5.6 類加值資料），而托嬰中心平均 0.0 類。
0–2 歲家長只能上托嬰中心或找保母，正好是資料最薄的一段。

與其讓他們瀏覽半天才發現什麼都沒有，首頁直接問「孩子多大了」並老實說
「這一段我們幫得有限」，同時給出社會局查詢與居家托育服務中心的入口。

### 機構頁最上面是概覽

頁面往下有收費表、補助試算、裁罰明細、官方連結四大段，每段都完整但也都要讀。
家長比較三五間時不會每間讀完，所以最上面放一組關鍵數字，五秒內回答
「這間值不值得再看下去」：補助後大約付多少、收不收我的孩子、有沒有裁罰、寒暑假、規模。

概覽的金額固定用第 1 胎、非低收、有資料的最小年齡，其他組合在下方試算區切換。
`verify.js` 有一條檢查確保概覽顯示的金額與試算結果一致，避免兩處各算各的。

### 成本監控

Firebase Spark 免費方案**無法設定用量警示**（那是 Blaze 限定），而超過每月 10 GB
的後果是**網站被停用到下個月**，不是收費——對一個家長臨時搜尋才會用到的網站，
斷線比帳單糟。

`npm run cost` 用實際的建置產物推估天花板，每次 build 會自動跑一次。

**一定要量壓縮後的大小。** 這裡踩過一次：第一版直接用檔案位元組數，算出來的天花板
比實際悲觀 8.6 倍（每日 457 vs 3,927 人次）。Firebase 會自動以 Brotli 傳輸，
而 HTML 與 JSON 都是高度重複的文字——520 KB 的搜尋索引實際只傳 44 KB。
錯的數字會導出錯的優化決策。

目前（雙北）的實測結果，皆為壓縮後：

| 訪客行為 | 每人傳輸 | 每日可服務 |
| --- | --- | --- |
| 看一頁就離開 | 9 KB | 37,517 |
| 首頁→行政區→3 間機構 | 34 KB | 10,423 |
| 同上再用一次搜尋 | 66 KB | 5,300 |
| 同上改用「附近」 | 70 KB | **5,013** |

### 索引依「用途」拆兩包，不是依縣市

量過才知道按縣市分片幾乎沒用——Brotli 對重複的中文壓縮率極高，
整包壓完只有 44 KB，拆成兩市各一包省不到幾 KB。

真正的浪費是搜尋頁一直在下載它從來不用的座標，而浮點數正好是壓縮率最差的東西。
所以 `search-index.json` 不含座標（44 → 32 KB），`geo-index.json` 只含有座標的
1,853 筆、也不帶搜尋才需要的縣市與類別（36 KB）。`verify.js` 有檢查確保兩邊
不會又混回去，否則等於白拆。

再下一步（前綴分片、大型行政區頁分頁）要等真的接近上限再做，現在是過早優化。

### 沒有資料時也要說「沒有」

機構頁的收費與裁罰兩個區塊**一律出現**，即使沒有資料。
「查過、沒有」和「這站根本沒查」對家長是完全不同的資訊——
早期版本只在有資料時渲染，結果托嬰中心的頁面上什麼都看不到，無從判斷。

### 招生時程的日期是寫死的，但會自己過期

`src/lib/admission.js` 是全站唯一手寫日期的地方。招生時程沒有任何開放資料——
它散在各市的招生網、簡章 PDF 與新聞稿裡，只能人工抄錄。

含糊的「大約四五月」對家長沒有用，他要的是能寫進行事曆的那一天，所以還是照抄了確切日期。
代價是這份資料會過期，而**過期的招生日期比沒有更糟**：舊日期看起來就像今年的，
家長照著準備就會錯過登記。

因此每組日期都綁學年度，頁面在建置時（`data.fetchedAt`）比對今天：
已結束的階段淡掉並標「已結束」，進行中的標出來。整個學年度都過完而下一年度還沒更新時，
頁面改成明講「這一輪已經結束」，並列出現在還能做的事（私立隨時可問、臺北托嬰隨時可候補、
先收藏起來），而不是把舊日期擺著假裝有效。網站每月自動重建，這個判斷會跟著更新。

抽籤與報到日只寫在簡章 PDF 裡，**刻意沒有抄錄**——抄錯的代價是家長白跑一趟，
那一段直接寫「以簡章為準」並附連結。

每年三、四月官方公告新學年度時，更新 `PRESCHOOL` 的 `year` 與各階段日期，
以及 `VERIFIED_ON`。`verify.js` 有五條檢查看著這頁：官方連結齊全、過期時要有可行動的替代方案、
日期格式與先後順序、以及首頁與頁尾都留有入口。

### 托嬰中心：評鑑、名額，以及一整類漏收的機構

翻過兩個市府平台後補上的。臺北市社會局有兩份沒被用到的資料集：
**托嬰中心評鑑結果**（逐年等第）與**準公共化托嬰中心**（核定／實際收托人數、準公共身分）。
後者順帶解決兩件事——「還有沒有名額」是招生時程頁原本明講查不到的，
而 **57 間社區公共托育家園**兩份托嬰名冊都不含，本站先前一間都沒收錄，
偏偏招生時程頁已經寫了臺北市的候補規則「限登記 1 家公辦民營托嬰中心與 1 家社區公共托育家園」。

**新北市什麼都沒有。** 掃過該平台 65 個資料集，社會局兒童托育科只公開名冊與訓練課程，
沒有評鑑、沒有準公共、沒有收托人數。而托嬰中心沒有幼兒園那種全國性的民間封存可以補。
所以首頁與機構頁都要講明這是資料落差、與機構品質無關——不能讓新北的家長誤會。

#### 名稱比對刻意不做子字串

市府幾份資料集對同一間機構用不同寫法：名冊寫「臺北市私立安筠托嬰中心(原名稱：小哈利)」、
準公共名單用舊名「小哈利」、評鑑名單省略市名寫「中山托嬰中心」、公辦民營則是
「臺北市政府社會局委託X協會經營管理臺北市Y托嬰中心」的全名。

`nameKeys()` 只做安全的變體：有無「臺北市」前綴、有無「私立」、括號註記與其中的舊名、
「經營管理／辦理」之後的核心名。並且 `buildNameIndex()` 有一條硬規則——
**一個鍵對到兩間不同機構就標為不明確、之後一律不採用**，行政區可作為消歧依據。

用子字串比對可以把命中率從 89% 推到 95% 以上，但「漢妮」與「漢妮明水園」、
「凱瑞莎」與「凱瑞莎青田」是不同分館，那會把甲館的評鑑等第掛到乙館頭上——
比不顯示糟得多。實測碰撞數 0。

殘留的 11% 不是比對失敗：拆開來看，22 間是市府名冊裡**查無此名**（評鑑名單與名冊
彼此對不起來），4 間是上述刻意放棄的分館。所以對不上的頁面會說明是名單對不起來，
而不是留白讓人以為評鑑不合格。

#### 評鑑等第照原文列出，本站不加判斷

來源有「甲」「甲等」「優」「優等」「丙(輔導通過)」甚至「因績優排除項目降為乙等」九種寫法，
一律照列不改寫。第一版程式把非甲的標成警示色，那與元件裡自己寫的
「本站只轉列結果，不做任何解讀或排名」直接矛盾——裁罰是客觀的不利事實，
評鑑等第是政府的評價，把「乙」標紅等於本站又加了一層判斷。已移除。

### 「每月必繳」是攤平的平均，不是付款節奏

`summary1` 的 `monthly1` 是全年總額 ÷ 月數——政府算平價教保上限也是用這個公式，
金額沒錯，但它把開學要一次繳的那一包攤平了。

實例：燕翔幼兒園原本只顯示「每月 14,783」，實際節奏是**開學繳 29,900、之後每月 9,800**。
驗算 `29,900×2 + 9,800×12 = 177,400`，正好是全年必繳。錢沒少，但一個照著 14,783
編預算的家長，一年會有兩次各短缺三萬。而且比較兩間園所時更糟：一間學費三萬、
一間平均分攤，在攤平後長得一模一樣。

分項只存在 `slip114`（園所依法申報的收費明細表），每間一個 JSON，每個項目帶「收費期間」，
分「學期」與「月」。解析有三個坑，全部踩過：

- **交通費是巢狀的單趟／雙趟兩欄**，直接取數字會把 2000 與 3000 黏成 `20003000`
- **交通費、課後延托費、家長會費不計入「全學期總收費」**，都是選繳
- **月數可以是小數**（5.5 個月），用去掉非數字的方式解析會變成 55

修正前 80 份只有 4 份對得上，修正後 754 筆收費組合 **100% 通過驗算**，
且與站上既有的 `monthly` 交叉比對 2,972 / 2,983 一致。實際涵蓋 **1,677 / 1,680 間（99.8%）**。

每一筆都要通過兩道驗算才會顯示：學期項＋月項＝園所申報的全學期總收費，
以及半年總額×2＝`summary1` 的全年必繳。對不上就不顯示——寧可少一欄，
也不要給家長一個算錯的「開學要繳多少」。涵蓋率低於 80% 直接中止建置。

**平價教保要另外講。** 公立／非營利／準公共的家長每月繳費有政策上限，繳的是上限
而不是園所申報的節奏，所以那些頁面顯示的是不同的說明——不講清楚，這張表反而會
嚇到本來負擔得起的家長。

代價：每次建置多約 1,680 次請求（約 90 秒）。沒有整包下載的捷徑，封存 repo 有 2.3 GB。

### 準公共要看契約年度，不能看屬性欄

**準公共不是一種設立屬性**——它是私立園跟政府簽的合約，約到期就回到私立。
用單一的「屬性」欄位表達它，三個來源都會出錯：

| 來源 | 問題 |
| --- | --- |
| 封存 GeoJSON 的 `type` | 只有私立／公立／非營利，準公共整批落在私立裡 |
| 封存 `summary1` 的 `type` | 有「準公共化」，但沒有「非營利」這個值 |
| 新北市開放資料的 `type` | 有準公共，但停在舊名單：漏掉 34 間新加入的、留著 5 間已退出的 |

封存 GeoJSON 另有 `pre_public` 欄位，值是**契約的起訖年度**（例如 `113-115`，無約為「無」），
所以能判斷「現在」算不算。`applyQuasiPublic()` 用它加上當下學年度（8 月換學年）決定屬性。
那個欄位就在本來就會下載的 GeoJSON 裡，**不用多打任何一次請求**。

實測新北市 1,110 間，它與市府資料只在私立↔準公共這條界線上有 39 間分歧，
**從不與公立／非營利／職場互助衝突**，所以只在這兩者之間切換是安全的——
那三類各有不同的繳費上限，誤動會直接算錯家長要付多少。

修正前臺北市 173 間準公共全被當成私立，自付額被高估中位數 6,174 元／月、最高 15,333；
例如小天心顯示「你付 18,333」，實際是 3,000。錯的方向最糟——把負擔得起的園所
顯示成負擔不起。修正後兩市共 490 間有效契約（新北 315、臺北 175）。

**期程換代的陷阱**：準公共是分期程簽約的，換代時整批契約同時到期。上游若沒跟上，
幾百間會無聲降級成私立，家長看到的自付額突然多出好幾千。所以 fetch 端在
「過期比例超過一半」時直接中止建置，verify 端另有一條檢查全站準公共數量沒有崩掉。
機構頁也會寫出契約年度與「合約分期程換約」的提醒。

### 腳本不能在被 import 時自己跑起來

`verify.js` 為了引用常數而 `import` 了 `fetch-data.js`，結果每次驗證都重新抓一次資料
並覆蓋 `institutions.json`——驗證的變成它自己剛寫出來的檔案，而不是建置實際使用的那份。
執行時間從 1 秒變成 35 秒才被發現。

純函式一律抽到 `src/lib/`（見 `quasi.js`），有 `main()` 的腳本一律加
`import.meta.url === \`file://${process.argv[1]}\`` 守衛。`verify.js` 有一條檢查掃過
`scripts/` 底下每個檔案確認這件事。

### 三隻看門狗：讓「沒有人在看」變成看得見

前面所有防護有個共同弱點——**它們都只在建置有跑的時候才有用**。這三個機制看的正是
建置沒跑、或跑了但沒人知道出事的情況。

**排程保活。** GitHub 會在 repo 連續 60 天沒有任何改動時自動停用 scheduled workflow，
而「網站運作良好」正好等於「沒有理由改動」——所以這件事會剛好在一切順利時發生，
而且不會有任何錯誤通知，因為工作流程根本沒被叫醒。所以排程跑完就把資料寫回 main：
`institutions.json` 裡的 `fetchedAt` 每次都變，永遠有 diff，不會因為「這個月開放資料剛好
沒異動」而失去保活。失敗時不寫壞資料進去，改往 `.github/run-log` 追加一行——否則
「管線壞了」會連帶變成「排程也被停用了」，而第二個問題是靜默的。只有排程執行才寫回，
手動 push 觸發的那次不寫，免得每次推完本機就落後一版。

**資料老舊自我揭露。** 判斷寫在 `src/scripts/staleness.js`，**在瀏覽器端執行**。
這是關鍵：要警告的情況正是「頁面沒有被重新產生」，那時候整站凍結，任何建置期算出來的
東西都不會更新，包括「這份資料已經很舊了」這句話本身。45 天頁尾加徽章，90 天每頁置頂
橫幅。訪客系統時鐘走錯時（負數或超過五年）一律安靜，不顯示「已 19,000 天未更新」。

**補助費率自動核對。** `scripts/check-subsidy.js` 每月比對教育部三個頁面。站上大部分數字
都是抓下來的，抓不到就消失；補助費率是寫死的政策數字，政策改了程式照樣算得出漂亮的
金額，只是錯的。官方表格是「歷次調整」的多欄結構，現行金額在最後一欄，所以表頭的
`111.8以後` 是比金額比對更早的哨兵——政策一調整就會多一欄。

**只偵測、不自動更新**：本檔第一版解析就抓錯欄位，把隔壁欄的 2,500 當成現行費率。
若讓它自動採用，那個錯誤會直接寫上網站。三種失敗分開處理，否則警語會變成狼來了：

| 狀況 | 站上 | 通知 |
| --- | --- | --- |
| `unreachable` 連不上 | 不動，且不改變既有結論 | 無 |
| `unreadable` 解析失敗 | 連續兩次才顯示 | 開待辦 |
| `mismatch` 數字不同 | 立刻在試算表格**之前**顯示警語 | 開待辦 |

偵測到問題**不擋建置**：擋下來不會讓線上那份錯金額消失，只會讓機構名冊、裁罰這些
沒問題的資料一起停止更新。待辦用固定標題去重，已經開著就完全不動作——同一個問題
每月寄一封，三個月後就沒人看了。

金額存在兩個檔案裡（`subsidy.js` 的 `CAPS`/`ALLOWANCE` 與 `check-subsidy.js` 的 `EXPECTED`），
只改一邊會讓偵測器對著錯的基準核對並回報「一切正常」——比沒有偵測器更糟。
`verify.js` 有一條檢查透過 `estimate()` 比對兩邊，擋住這件事。

**這三隻狗自己也要被測。** 它們平常完全靜默，而壞掉的偵測器跟正常的偵測器從外面看
一模一樣——那正是它們要消滅的失敗模式，只是往上搬了一層。`verify.js` 用假資料餵進去：
每個金額逐一改掉都必須響、多一欄必須響、讀不到必須丟 `UnreadableError`（而不是隨便一個
TypeError，否則三級分類會退化成一級）、連不上不能洗掉連續失敗計數、修好後警語要消失。

### 部署後的煙霧測試

`scripts/smoke.js` 在部署之後實際連線上網站。在這之前沒有任何一步看過
`https://alongside-53f07.web.app` 究竟回了什麼——驗證檢查的是 `dist/` 裡的檔案，
部署步驟只回報「上傳沒有出錯」。檢查首頁是否帶有本次建置的 `fetchedAt`，
而不只是「有回 200」，否則 CDN 給舊的也會通過。

## 兩個容易踩到的地方

**三個資料集的地址格式不一樣。** 幼兒園是 `[220]新北市板橋區流芳里9鄰東門街30號`（含郵遞區號、縣市、
行政區、里鄰），托嬰與公托只有街段 `莊敬路46號2樓`。`toStreet()` 統一剝成街段再自己組回去。
剝除一律只在字串開頭做——實測有街名叫「區運路」，任何「切到第一個『區』字」的寫法都會把它砍壞。
另有少數資料用了異體字「新北巿」（U+5DFF）、地址中夾換行，都已處理。

**幼兒園和托嬰中心歸不同主管機關。** 幼兒園是教育部／新北市教育局，托嬰中心與公托是衛福部／新北市社會局，
兩套查詢系統完全獨立，官方連結必須依 `authority` 分開給。教育部那三個查詢頁是 ASP.NET POST 表單，
沒辦法用網址帶入園名，所以機構頁要先提供「複製機構名稱」按鈕。

## 免費額度的懸崖（刻意不做監控）

Firebase Spark 每月 10 GB，超過整站關到下個月，且**無法設定用量警示**。
`npm run cost` 實測要每日約 5,006 人次才會觸及上限——以目前流量非常遠，
現在做監控是推測性工程。取而代之：**Search Console 的每日點擊接近 2,000 時就該處理**。
真的接近了再說，那時候是個好問題。

## 成本紅線

只用 Firebase Hosting，不啟用 Cloud Functions / Firestore / Storage——那些會被推去綁信用卡的 Blaze 方案。
資料抓取與建置都在 GitHub Actions（免費額度內）完成，上線後的網站不依賴任何後端服務。

地圖與評價走 Google 地圖「連結」，家長點擊才由他們的瀏覽器開啟 Google，本站不呼叫任何 API，無金鑰、無用量、無費用。
